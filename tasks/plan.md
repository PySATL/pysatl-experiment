# План: генерация обучающих выборок со случайными параметрами

## Цель

Добавить в `pysatl-experiment` отдельный режим `generation_only`, который для каждой новой выборки независимо выбирает параметры распределения, генерирует наблюдения и сохраняет в SQLite как саму выборку, так и фактически использованные параметры.

На первом этапе поддерживаются только восемь распределений: normal, exponential, weibull, gamma, beta, lognormal, student и uniform. Расчёт критериев и подготовка 158 ML-признаков остаются задачей `pysatl-expert` и не входят в эту доработку.

## Что показал аудит текущего кода

- Сейчас доступны только `critical_value`, `power` и `time_complexity` (`configuration/models/experiment_type.py`, `cli/commands/build_and_run.py`).
- `GenerationStepData` содержит один готовый генератор и один фиксированный список параметров. Все выборки задания генерируются с ними же (`experiment_execution/step/generation.py`).
- Генерация сначала накапливает весь пакет выборок в памяти, а затем сохраняет его. Для длительной генерации обучающего набора это лишний риск по памяти и при прерывании процесса.
- Таблица `random_values` идентифицирует запись по имени генератора, фиксированным параметрам, размеру и номеру выборки. Связи с конкретным запуском нет (`persistence/random_values_storage.py`).
- `experiments` и `random_values` уже обслуживают CV/power-пайплайн; автоматических миграций схемы нет, используется только `metadata.create_all()` (`persistence/db_store/model.py`). Изменение этих таблиц опасно для существующей большой базы.
- Генераторы восьми выбранных законов уже существуют, но их `generate(size)` не принимает локальный RNG/seed. Нижележащие функции `pysatl-criterion` вызывают `scipy.stats.*.rvs` без `random_state`, поэтому воспроизводимое независимое продолжение генерации сейчас не обеспечивается.

## Предлагаемый контракт конфигурации

Один конфигурационный файл описывает один закон распределения. Для восьми законов создаются восемь запусков — это минимально меняет существующую архитектуру и упрощает повторный запуск только упавшей части.

```json
{
  "name": "normal_training_samples",
  "config": {
    "experiment_type": "generation_only",
    "distribution": "normal",
    "sample_sizes": [100],
    "samples_count": 10000,
    "parameters": {
      "mean": {"type": "random_uniform", "low": -5.0, "high": 5.0},
      "var": {"type": "random_uniform", "low": 0.5, "high": 5.0}
    },
    "seed": 20260912,
    "run_mode": "reuse",
    "storage_connection": "sqlite:///training_samples.sqlite"
  }
}
```

Параметр в первой версии имеет один из двух явных типов:

- `{"type": "fixed", "value": ...}` — фиксированное конечное число;
- объект `{"type": "random_uniform", "low": ..., "high": ...}`.

Другие правила случайного выбора в первую версию не входят. Имена параметров должны быть явными, а не позиционным списком.

## Границы параметров

Конфигурация должна отклоняться до любых записей в БД, если неизвестно имя параметра, границы не конечны или возможны недопустимые значения.

| Распределение | Параметры | Ограничения |
|---|---|---|
| normal | `mean`, `var` | `mean` конечен, `var > 0` |
| exponential | `lam` | `lam > 0` |
| weibull | `a`, `k` | `a > 0`, `k > 0` |
| gamma | `alfa`, `beta` | `alfa > 0`, `beta > 0` |
| beta | `a`, `b` | `a > 0`, `b > 0` |
| lognormal | `s`, `mu` | `s > 0`, `mu` конечен |
| student | `df` | `df > 0` |
| uniform | `a`, `b` | гарантировать `a < b` для всей заданной области |

Для uniform в v1 диапазоны принимаются только тогда, когда `max(a) < min(b)`. Это исключает повторный случайный выбор и неявное искажение заданного распределения параметров.

## Хранение данных

Не изменять существующие таблицы `experiments` и `random_values`. Добавить изолированную схему:

### `generation_runs`

- `id`;
- имя запуска;
- тип распределения;
- размеры выборок;
- количество выборок на каждый размер;
- исходная конфигурация параметров в JSON;
- корневой `seed`;
- стабильный fingerprint существенной части конфигурации;
- состояние запуска.

### `generated_samples`

- `id`;
- `generation_run_id`;
- `sample_size`;
- `sample_num`;
- фактически использованные именованные параметры в JSON;
- сжатый массив наблюдений;
- при необходимости производный seed конкретной выборки.

Уникальность: `(generation_run_id, sample_size, sample_num)`. Исходные диапазоны хранятся один раз в `generation_runs`, фактические параметры — в каждой строке `generated_samples`.

Истинные параметры являются метаданными и целевой диагностикой. По умолчанию они не включаются в ML-признаки, иначе модель получит информацию, которой нет у реальной неизвестной выборки.

## Этапы реализации

### 1. Зафиксировать конфигурационный API

- Добавить `generation_only` в `ExperimentType` и CLI-discriminated union.
- Создать отдельную Pydantic-модель режима, не требующую `criteria`, `significance_levels`, executor и report builder.
- Добавить типы fixed/random_uniform и проверку допустимых параметров восьми распределений.
- Добавить legacy/dataclass-адаптер только там, где он действительно нужен фабрике.
- Добавить пример JSON и тесты валидной/невалидной конфигурации.

### 2. Добавить изолированное хранилище

- Создать модели и хранилище для `generation_runs` и `generated_samples`.
- Переиспользовать `CompressedFloatArray` для данных выборки.
- Реализовать создание запуска, вставку одной выборки, подсчёт/поиск существующих номеров и чтение данных для будущего потребителя.
- Не выполнять миграцию и не открывать на запись существующую CV-базу в ходе разработки и тестов; все тесты проводить на временной SQLite.

### 3. Сделать воспроизводимую генерацию

- Для каждого `(root_seed, distribution, sample_size, sample_num)` детерминированно получать независимые RNG для параметров и наблюдений.
- Добавить необязательный `random_state` в генераторный путь для восьми распределений. Предпочтительный вариант — сначала аддитивно расширить соответствующие функции `pysatl-criterion`, затем прокинуть аргумент через генераторы `pysatl-experiment`; старые вызовы без аргумента должны работать как прежде.
- Проверить равенство параметров и выборок при повторном запуске с тем же seed.

Этот пункт затрагивает публичные сигнатуры `pysatl-criterion`, хотя и обратно совместимо. Перед его реализацией нужен отдельный короткий review/подтверждение.

### 4. Реализовать отдельный generation-only step

- Перед каждой выборкой получать новые фактические параметры.
- Создавать генератор с этими параметрами и сразу сохранять одну выборку, не удерживая весь пакет в памяти.
- Привязать запись к запуску и сохранить точные именованные параметры.
- При `reuse` пропускать уже сохранённые номера; производные seed должны гарантировать, что продолжение не меняет оставшуюся последовательность.
- При `overwrite` удалять только данные точно найденного generation-run и только после явного выбора этого режима.

Старый `GenerationStep` и его CV-семантика остаются без изменений.

### 5. Подключить режим к CLI

- Добавить фабрику `GenerationOnlyExperimentFactory` и зарегистрировать её в `build_and_run`.
- Для нового режима создавать только generation step; вычисление статистик, CV и отчёта не запускать.
- Завершённость определять по generation-run, а не требовать флагов execution/report.

### 6. Проверить обратную совместимость и устойчивость

- Unit-тесты параметрических политик и ограничений всех восьми распределений.
- Storage-тесты на временной SQLite: round-trip конфигурации и фактических параметров, уникальность, resume и изоляция запусков.
- Тесты, что параметры выбираются заново для каждой выборки и остаются в диапазоне.
- Тесты воспроизводимости одинакового seed и различия разных seed.
- Тест прерывания/повторного запуска без дублей и перезаписи существующих строк.
- Регрессионные тесты существующих CV, power и time-complexity фабрик.
- Запустить `poetry run pytest` и `poetry run ruff check .`; тяжёлую генерацию не запускать.

## Критерии готовности

- Режим `generation_only` не вычисляет критерии и критические значения.
- Для каждой выборки параметры выбираются независимо и сохраняются вместе с ней.
- Исходная политика/диапазоны и seed сохраняются на уровне запуска.
- Один seed и одна конфигурация дают одинаковый результат, в том числе после возобновления.
- Процесс можно продолжить без дублей после прерывания.
- Генерация сохраняет данные потоково и не держит весь набор в памяти.
- Существующие CV/power/time-complexity режимы и таблица `random_values` не меняют поведения.
- Все проверки выполняются на временной БД; существующая большая SQLite-база не модифицируется.

## Не входит в эту задачу

- вычисление 158 статистик;
- оценка параметров гипотез при вычислении статистик;
- формирование матрицы признаков и обработка NaN/inf;
- обучение или изменение `HierarchicalExpertModel`;
- кластеризация семейств и top-3 инференс;
- добавление недавно появившихся распределений сверх согласованных восьми.

## Миграция на актуальный `main`: универсальный режим генерации

Этот раздел заменяет ограничение «восемь распределений» выше. После обновления
`pysatl-experiment` до `origin/main` режим `generation_only` должен поддерживать
каждое распределение, для которого `pysatl-criterion` предоставляет одновременно
descriptor параметров и RVS generator. Новое распределение не должно требовать
изменений в `pysatl-experiment`.

### Канонические API

- `DistributionType` — единственный публичный идентификатор распределения;
  JSON использует его `.value` (например, `log_normal`, а не прежний alias
  `lognormal`).
- `get_available_distribution_descriptor(distribution)` сообщает полный список
  имён параметров, дефолтов и валидаторов.
- `get_available_generator(distribution, params)` создаёт generator через
  discovery subclasses, без локальной таблицы generator-классов.

`pysatl-experiment` не дублирует таблицы имён параметров, положительности,
вероятностей, generator-классов или кодов seed. Валидаторы descriptor применяются
к границам каждой параметрической политики; любые межпараметрические ограничения,
которых descriptor не выражает, должны быть проверены при создании generator и
сообщены как ошибка конфигурации до записи в SQLite.

### Совместимость с новым experiment pipeline

`generation_only` подключается так же, как остальные типы:

```text
CLI -> validate_build_and_run -> GenerationOnlyExperimentData
    -> GenerationOnlyExperimentFactory -> ExperimentSteps
    -> Experiment.run_experiment
```

Factory создаёт только generation step. Execution и report steps остаются `None`;
runner уже пропускает отсутствующие steps. При этом режим сохраняет samples в
изолированные `generation_runs` / `generated_samples`, а не в legacy
`random_values`.

### Зависимость от `pysatl-criterion`

Нынешний генераторный API имеет только `generate(size)`. Для детерминированного
generation-only требуется обратно совместимый аргумент
`random_state: numpy.random.Generator | None = None` во всех concrete generators
и нижележащих `rvs`-вызовах. Старые вызовы без аргумента должны сохранить текущее
поведение. Это отдельный атомарный слой миграции: experiment не должен подменять
глобальный RNG или реализовывать локальные копии generators.

### Вертикальные задачи

1. Сначала разрешить только конфликт Pydantic boundary: заменить удалённый
   `Hypothesis` на `DistributionType`, принять canonical JSON IDs и получать
   допустимые имена параметров из descriptor.
2. Добавить в `pysatl-criterion` аддитивный `random_state` и contract tests для
   каждого dynamically discovered generator.
3. Перенести `GenerationOnlyExperimentConfig`, `ExperimentData`, factory и CLI
   registration на новые каталоги `experiment_config` / `experiment_factory`.
4. Перенести generation step: через canonical generator API выбрать параметры,
   stream-ить samples и сохранять точные realised parameters в изолированное
   storage.
5. Подключить resume/overwrite к `GenerationRun`, не затрагивая существующие
   CV/power/time-complexity storage и не изменяя пользовательские SQLite-артефакты.
6. Проверить discovery: тест, добавляющий test-only descriptor/generator, должен
   доказать отсутствие изменений в `pysatl-experiment`; добавить end-to-end test
   для реального distribution из `DistributionType`, которого не было в старых
   восьми.

### Принятое решение: изолированные данные, общий запуск

`generation_runs` и `generated_samples` остаются единственным хранилищем
конфигурации и данных `generation_only`. Запуск подключается к общему
`ExperimentSteps` pipeline через небольшой контракт статуса: после успешного
generation step runner отмечает завершение соответствующего `GenerationRun`.

Мы не создаём фиктивную запись в `experiments` и не записываем training samples
в `random_values`: эти таблицы описывают CV/power/time-complexity эксперименты с
фиксированной конфигурацией генератора. Изолированные samples могут позднее
быть явно экспортированы отдельным адаптером, но не подменяют CV-входные данные
неявно.
